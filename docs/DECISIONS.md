# 未決事項と調整ポイント

このシステムは、設計時に **勝手に決めない** べき項目を明記しています。

運用・実装フェーズで、実際の使用状況を見ながら調整します。

---

## 未決事項 1: 通知先（Slack / LINE Messaging API / メール）

### 現状

- **実装済み**: Slack Bot（notifier/slack/）
- **参考実装**: コンソール出力、JSON 保存

### 選択肢

| 選択肢 | メリット | デメリット | 推奨フェーズ |
| --- | --- | --- | --- |
| Slack | リアルタイム、スレッド対応、ユーザーが見やすい | Slack ワークスペース必須 | Phase 1（現在） |
| LINE Messaging API | スマートフォン対応、広がりやすい | 連携設定が複雑 | Phase 2 |
| メール | 古い環境にも対応、ログとして残る | リアルタイム性が落ちる | Phase 2 |
| Webhook カスタム | 完全自由、カスタマイズ性高い | 実装者次第 | Phase 3 |

### 決め方

1. **当面は Slack** に集約（ユーザーが見やすい）
2. **API（JSON）は共通** なので、ユーザーが LINE/Mail を追加実装可能
3. **複数通知先を同時に使う必要が出たら、別リポジトリで実装例を公開**

### アクション

- 1ヶ月運用後、ユーザーフィードバックを集約
- 追加通知先の要望が多い場合は、reference implementation を複数公開

## 未決事項 2: 即時通知と集約通知の厳密な境界

### 現状（仮）

**src/config/severity.json で定義中：**

| レベル | 情報名（例） |
| --- | --- |
| **immediate** | 津波警報・注意報、特別警報、噴火警報、地震（震度5弱以上）、大雨・洪水・土砂災害の危険警報（レベル5） |
| **digest** | 暴風・波浪・大雪警報、土砂災害危険警報（レベル4）、高潮警報 |
| **record** | すべての注意報、気象防災速報、定時情報 |

### 不確実性

- **「危険警報」と「警報」の区別**: 2026年5月の体系変更で、命名がまだ定着していない
- **地域ごとの優先度**: 沿岸地域は津波を重視、内陸は洪水を重視（すべてに対応できないか？）
- **荒天時の集約間隔**: 数分単位の警報乱発時に、5分集約では多すぎないか？

### 決め方

1. **Phase 0（Phase 1実装済み）で全国運用データを実測**
   - 実際の警報・注意報発表パターンを分析
   - false positive（過剰通知）の程度を測定

2. **運用 1ヶ月間は fixed boundary で実施**
   - severity.json を固定
   - 毎日ログから境界の適切性を検証

3. **運用後、以下に基づき調整**
   - 同一地域で「即時」「集約」が同時発表 → 集約基準が甘い
   - 平時にノイズが多い → 即時基準が低い

### 設定ファイル

```json
{
  "immediate": {
    "keywords": ["津波", "特別警報", "噴火警報"],
    "minEarthquakeSeverity": 5,
    "dangerLevelMin": 5
  },
  "digest": {
    "keywords": ["暴風", "波浪", "大雪"],
    "dangerLevelMin": 4
  },
  "record": {
    "keywords": ["注意報", "予報"]
  }
}
```

**すべてが設定から外に出ている → 実装を変えなくても調整可能**

### アクション

- 1ヶ月の運用ログを分析（通知件数、タイプ別集計）
- 実測の false positive 率に基づき、severity.json を修正
- git commit で履歴を残す

## 未決事項 3: 集約通知の間隔と夜間の扱い

### 現状

- **集約通知の間隔**: 5分（GitHub Actions のスケジュール）
- **夜間の扱い**: 24時間常時実施

### 問題

| 問題 | 背景 | 影響 |
| --- | --- | --- |
| 深夜の通知 | 5分ごとの Slack 通知が、夜中でも来る | ユーザーが睡眠を妨害されないか |
| 集約間隔が短すぎ | 5分では、激しい天気の場合に複数通知 | ユーザーが見落とさないか |
| 集約間隔が長すぎ | 15分だと、重要な警報の遅延が大きい | リアルタイム性が失われないか |

### 候補案

| 案 | 実装 | メリット | デメリット |
| --- | --- | --- | --- |
| A) 24時間5分固定 | 現在のまま | シンプル | 深夜通知あり |
| B) 時間帯別 | 9時～22時は5分、他は15分 | 深夜通知削減 | スケジュール複雑化 |
| C) 平日/休日別 | 平日は厳しく、休日は緩く | 勤務形態に対応 | 運用難 |
| D) Digest を廃止 | immediate だけ通知 | 余計なノイズなし | 重要情報を見落とすリスク |

### 決め方

1. **デフォルトは A（24時間5分固定）**で運用開始
2. 1ヶ月後に以下をログで確認：
   - 22時～6時の通知件数
   - その時間帯での false positive 率
   - ユーザーフィードバック

3. 深夜通知が問題なら **案B に切り替え**

### 実装上の考慮

GitHub Actions では複数 cron スケジュール可能：

```yaml
# 複数スケジュール案
schedule:
  - cron: '*/5 9-22 * * *'   # 9時～22時は5分ごと
  - cron: '*/15 22-9 * * *'  # それ以外は15分ごと
```

## 未決事項 4: 注意報を記録対象に含めるか、完全に捨てるか

### 現状

注意報は `record` レベル = **通知はしないが JSON には含める**

```json
{
  "timestamp": "...",
  "feeds": [
    {
      "feed": "extra",
      "entries": [
        { "title": "大雨注意報", ... },  // 記録対象に含めている
        { "title": "暴風警報", ... }     // 即時通知対象
      ]
    }
  ]
}
```

### 問題

| 選択 | メリット | デメリット | JSON 容量への影響 |
| --- | --- | --- | --- |
| **含める（現在）** | 履歴が完全、統計分析に有用 | JSON ファイルが大きくなる | +約20～30% |
| **捨てる** | JSON がコンパクト | 事後分析が限定的 | 容量削減 |

### 実測（参考）

Phase 0 実測から：

- 日中（天気悪い日）: 注意報 200件 / 警報 50件（4倍）
- 通常時: 注意報 10件 / 警報 2件（5倍）

**注意報は警報の 4～5倍の量。**

### 決め方

1. **当面は含める** — JSON 容量より、データ完全性を優先
2. 月間アーカイブが 100MB を超えたら、以下を検討：
   - 古い注意報を削除する cleanup workflow
   - 注意報を分離したファイルに保存
   - 「注意報なし」オプション付き API

### アクション

- 月単位でアーカイブ容量を監視
- git リポジトリサイズが 1GB に達したら、archive cleanup ポリシーを導入

## 実装時のチェックリスト

システム拡張時に、この未決事項を **必ず確認**：

### 新しい通知先を追加する場合

- [ ] 未決事項1 を確認（通知先の方針）
- [ ] 既存 Slack 実装に倣う（notifier/ 配下に新フォルダ）
- [ ] ユーザーに opt-in を強制（Secret 設定が必要）
- [ ] テスト環境で dummy webhook で検証

### 深刻度分類を変更する場合

- [ ] 未決事項2 を確認（即時/集約の境界）
- [ ] severity.json を git commit で履歴化
- [ ] 変更理由を commit message に記載
- [ ] 運用ログ（通知件数）と合わせて記録

### 集約通知の間隔を変更する場合

- [ ] 未決事項3 を確認（5分/15分/時間帯別）
- [ ] .github/workflows/poll-jma.yml のコメントに理由を記載
- [ ] 変更前後の通知件数を比較記録

### 注意報の扱いを変更する場合

- [ ] 未決事項4 を確認（含める/捨てる）
- [ ] 月間アーカイブ容量と実用性を天秤にかける
- [ ] ユーザーに事前通知

## 参考: 勝手に決めてはいけないこと（教訓）

> 設計時に「これが最適」と仮定して実装しても、**実運用では想定外の使われ方が必ず出てくる。**

このプロジェクトで「勝手に決めない」としているのは、過去のシステム開発で、以下のような失敗を見てきたから：

- 😞 「注意報も通知する」と決めたら、夜中に数百通来て運用が破綻
- 😞 「完全な情報を JSON に入れる」としたら、ファイルサイズが肥大化してアーカイブが不可能に
- 😞 「特定地域だけにする」と仕様書に書いたら、ユーザーは全国対応を期待していた

→ **最初は引き算を優先し、必要なものだけ足す。調整は運用フェーズで。**
