# システム設計

気象庁防災情報 REST API システムの設計思想と判断根拠です。

## 最大の設計課題

> **取り込みは全国全件、通知は厳しく絞る。** ここを取り違えると失敗する。

### なぜこうするのか

気象警報・注意報は府県予報区ごと（全国で約140区）に発表され、荒天時はそれぞれが短時間に何度も更新される。地震も1回の揺れで震度速報・震源に関する情報・震源震度情報と複数の電文が連続する。

**全件を素通しで通知すると、悪天候の日には数百通が並び、通知が多すぎて誰も見なくなる。** これが本システムで最も現実的な失敗モードである。

したがって、通知量を減らすための以下3つの仕組みは、あとから足す機能ではなく **最初から設計に組み込む必要がある。**

## 3つの核となる仕組み

### 1. 状態差分ベース（イベント型ではなく）

**問題**: 気象警報・注意報の電文は差分ではなく、**その府県予報区の現在の全状態**が毎回入っている。素直に処理すると「変化のない再送」まで通知してしまう。

**解決法**: 府県予報区ごとの現在状態（発表中の警報・注意報の集合）を管理し、前回状態と比較して以下が起きたときだけ通知する：
- 新規発表（新しい警報が追加）
- 格上げ（注意報 → 警報）
- 格下げ（警報 → 注意報）
- 解除（発表中だったものが消える）

**効果**: 
- 同じ警報が何度も再送されても、変化がなければ通知しない
- 真の変化だけを捕捉
- 通知の信頼性向上（狼少年効果の回避）

### 2. 深刻度による通知経路の分岐

すべての情報を同じ優先度で扱うのではなく、情報の深刻度に応じて通知方法を変える：

| 段階 | 対象 | 扱い | 理由 |
| --- | --- | --- | --- |
| **即時** | 特別警報、津波警報・注意報、噴火警報、震度5弱以上、各危険警報 | 1件ずつ即通知 | 命に関わるため、即座に知らせる必要 |
| **集約** | 警報クラス（暴風・波浪・大雪等の警報） | 5～15分ごとに1通へまとめる | 重要だが、数分の遅延は許容可能。複数件まとめて通知でノイズ削減 |
| **記録のみ** | 注意報、定時情報 | Firestore に記録、通知しない | 参考情報。通知すると過度に多くなる |

**効果**:
- ユーザーが真に必要な情報に集中できる
- 通知の頻度と重要度が相関する
- 情報の優先度が明確

**調整ポイント**: 段階の境界は運用しながら調整する必要がある（→ [docs/DECISIONS.md](DECISIONS.md) 参照）。

### 3. EventID による束ね

**問題**: 地震の続報は `Head/EventID` が同一。続報のたびに新規メッセージを送ると、通知が増殖する。

**解決法**: 1事象＝1通知として扱い、続報は **メッセージの更新**（Slack なら `chat.update`）で反映する。新規メッセージを積まない。

**効果**:
- 同一イベントの複数電文を1つの通知にまとめる
- Slack の thread や pin で情報が集約される
- 通知数の過度な増加を防止

## 情報提供と通知の分離

### 設計判断

このシステムは **情報取得・整理・JSON提供** に徹し、**通知はカスタマイズ可能** にする。

- **このシステム（emergency-alert）**: 気象庁フィード → JSON API
- **利用者のシステム**: JSON を fetch → 自由に通知実装（Slack, LINE, Mail, 独自等）

### メリット

1. **疎結合**: 情報源と通知先が独立
2. **再利用性**: 複数の通知先で同じデータを使用可能
3. **カスタマイズ性**: ユーザーが自分たちの要件に合わせて実装
4. **スケーラビリティ**: 新しい通知先を追加しても core system は変わらない

### API の役割

```
気象庁フィード → [本システム] → JSON/REST API
                                    ↓
                    ┌───────────────┼───────────────┐
                    ↓               ↓               ↓
                Slack Bot       LINE Bot        カスタム
```

## 全国運用での設計

### 取り込み: 全国全件

- 4フィード（extra, eqvol, other, regular）から全エントリを取得
- 重複排除で、同一電文URLは一度だけ処理
- 地域制限なし

### 通知: 厳しく絞る

- 深刻度分類で、軽い情報は通知しない
- 状態差分で、変化がないものは通知しない
- EventID 束ねで、続報の乱立を防止

### ユーザーが地域フィルタを追加可能

API の JSON に地域コード（都道府県、市町村等）が含まれるため、利用者は自分の地域だけを通知する処理を実装可能。

## 技術選択の根拠

### GitHub Actions + REST API （Google Cloud 不使用）

**理由**:
- シンプルさ: Cloud Functions/Firestore/Scheduler の学習曲線不要
- コスト: GitHub Actions は月2,000分まで無料
- 運用性: git push で履歴管理、ロールバック容易
- スケーラビリティ: 初期段階では GitHub の容量で十分

**トレードオフ**: Firestore の状態管理がないため、セッション内で重複排除。その代わり ETag キャッシュで気象庁サーバーアクセスを最小化。

### Atom XML パース（fast-xml-parser）

**理由**:
- 気象庁が提供する標準フォーマット
- `entry` の `id` がそのまま重複排除キーになる
- `updated` が ISO 8601 形式で比較可能

### JSON ファイル（GitHub raw content URL）

**理由**:
- REST API として無料・無認証で公開可能
- バージョン管理が自動（git commit）
- キャッシュ時間制御可能（HTTP ヘッダ）
- 別リポジトリ不要（このリポジトリの api/ フォルダで十分）

## 未来への拡張性

### 現在は GitHub Actions ですが、スケーリング時に以下へ移行可能

| 段階 | 構成 | ポーリング間隔 |
| --- | --- | --- |
| **Phase 1（現在）** | GitHub Actions | 5分 |
| **Phase 2** | Cloud Functions gen2（Google Cloud） | 1分 |
| **Phase 3** | Pub/Sub ベース（非同期処理） | 毎秒単位 |

システムの core logic（状態差分、深刻度判定）は純粋関数で書かれているため、実行環境を変えても再利用可能。
